01 · Two-stage Delivery

전체 흐름은 2단계다 — 기술적으로 성립시키고, 그 다음 서비스로 출시한다

STEP 1 · CURRENT PROJECT

Player 개발 + 개발환경 구축 + 기술 검증

Target별 Player를 구현하고 Build → Deploy → Debug → 실제 Stream/DRM 재생까지 성립시킨다.

일반적인 “되면 좋고 아니면 말고” PoC가 아니다. 실제 서비스에 가져갈 Player가 되어야 하며, 문제가 있으면 구현 방식·버전·Adapter·지원 하한을 조정해 기술적 해법을 만든다.

결과: Player 구현 · 개발/검증 환경 · Target별 지원조건/제약 · 검증 Evidence

STEP 2 · SERVICE RELEASE

전체 서비스 통합 + 상용 검증 + 배포

1단계에서 검증된 Player를 실제 App·BFF/SDUI·인증·CDN·Production DRM·Analytics와 통합한다.

E2E/회귀/장시간/네트워크/실제 콘텐츠 검증을 수행하고, 플랫폼별 Certification · Store/Publisher · Commercial Release 절차를 거친다.

결과: 상용 서비스 App · 플랫폼 인증 · Store/서비스 배포 · 운영체계

두 단계의 경계가 중요하다. 1단계는 출시 검증이 아니지만 prototype 품질도 아니다. 2단계에서 버리지 않고 그대로 통합할 Player와 검증 기반을 만드는 단계다.
02 · Architecture Hypothesis

공통 Player Contract는 “하나의 인터페이스 코드”가 아니라 언어 중립 재생 계약이다

기존 PlayerAdapter 패턴을 멀티플랫폼으로 확장하는 설계 가설. 공통 의미를 먼저 정의하고 각 실행 계열이 자기 언어와 실제 Player로 구현한다.

PLAYER CONTRACT SPEC · LANGUAGE-NEUTRAL

Command load · play · pause · seek · stop   /   State idle · loading · ready · playing · paused · ended · error
Event stateChanged · trackChanged   /   Error source · drm · decode · network · unsupported   /   Capability offline · PiP · DASH · DVR · lowLatency …

ANDROID EXECUTION FAMILY

Kotlin Interface → Android PlayerAdapter

같은 Contract를 Kotlin으로 구현하고 Media3 / ExoPlayer에 연결. STB 내부는 MW·TIS·mABR·unicast로 추가 분기 가능.

APPLE EXECUTION FAMILY

Swift Protocol → Apple PlayerAdapter

동일한 계약을 Swift로 구현하고 AVPlayer / AVFoundation에 연결. iOS·tvOS의 공통화 범위를 검증한다.

WEB EXECUTION FAMILY

TypeScript Interface → Web PlayerAdapter

동일한 계약을 TypeScript로 구현하고 Shaka / MSE / EME에 연결. Browser·SmartTV·Console 호환 경계를 검증한다.

공유하는 것은 소스코드가 아니라 계약의 의미·데이터 모델·검증 기준이다. 1단계에서 세 실행 계열을 Conformance Test로 검증하고 Contract/Adapter 경계를 조정한다. Flutter는 네 번째 Player가 아니라 Android/Apple Adapter를 호출하는 Facade/Bridge 후보다.
03 · App × Player Co-work

같은 Target Matrix를 두 팀이 다른 목적에서 읽고, 지원조건은 함께 닫는다

App팀의 Device List는 21개 요구항목을 실제 기기·OS·조달 단위로 세분화한 기준선이다. Player팀은 같은 Target을 재생 실행계열·DRM·Runtime·검증환경 관점에서 다시 본다.

05 · Support Floor & Verification

“지원 하한”은 하나가 아니다 — Build · 재현 가능한 검증 · 서비스 지원을 구분한다

App팀 Matrix가 드러낸 핵심이다. RFQ에 적힌 최소 OS가 빌드되더라도 현재 Toolchain이나 실기에서 재현하지 못하면 Player팀은 그 버전을 검증 완료로 선언할 수 없다.

01 · BUILD FLOOR

코드가 빌드되는 하한

예: Fire OS 5가 API 22를 요구하면 Kotlin build/minSdk 하한에는 영향을 줄 수 있다. 하지만 이것만으로 서비스 지원을 의미하지 않는다.

02 · VALIDATION FLOOR

실제로 재현·검증 가능한 하한

예: App팀 자료는 Android TV 7·Android 7 고착 실기 확보가 어렵고, iOS 14/tvOS 12는 현 툴체인에서 재현 검증이 어렵다고 본다. 검증 Evidence가 가능한 지점을 따로 잡아야 한다.

03 · SERVICE FLOOR

최종적으로 약속할 지원 하한

App Runtime/UI + Player/DRM/Codec + 실제 기기 검증을 모두 통과한 뒤 확정한다. 필요하면 RFQ 하한을 TIM과 재협의한다.

플랫폼마다 하한을 닫는 방법도 다르다. Tizen/webOS는 구형 TV의 OS가 고정돼 실기로 하한을 재현하기 쉽지만, Android/Apple은 OS 업데이트·서명/Toolchain 때문에 과거 버전 재현이 어려울 수 있다. 지원 선언은 App과 Player 양쪽 Evidence가 있어야 한다.
06 · Android & Fire Family

기존 STB 강점을 기준선으로 쓰되, Retail·Fire·Vega는 같은 범위라고 가정하지 않는다

REFERENCE · OPERATOR STB

팀의 기준 자산

6종 STB에서 OEMCrypto · MediaCas · TIF/TIS · Tuner HAL · SoC/GPU · MW 범위를 확보한다. F1 DTT/CAS · F2 mABR · F3 IP가 이번 확장의 기준선이다.

ANDROID / FIRE OS

51 재사용 범위 검증

Retail Android TV와 Fire OS는 Android Studio/ADB 기반으로 접근 가능하나 세대·API·Widevine L1/L3·HEVC HW decode가 다르다. App팀은 Fire OS 5가 API 22 build 하한을 정할 가능성을 제시한다.

SCOPE GATE · VEGA OS

Fire Stick 이름만 보고 Android로 묶지 않는다

App팀 Matrix는 Vega OS를 Linux 기반 자체 OS·React Native 계열로 분리하고 범위 미정으로 둔다. 포함되면 기존 61/Kotlin 범위를 벗어나므로 App stack과 Player runtime을 모두 재판정해야 한다.

공동 체크: Retail Android TV 7/Android 7은 빌드는 가능해도 하한 실기 확보가 어렵다는 App팀 분석이 있다. Player팀은 API 하한과 “검증 가능한 서비스 하한”을 분리해 실기 결과를 제공한다.
07 · Mobile & Apple

모바일·tvOS는 Player 재사용과 “과거 OS를 실제로 검증할 수 있는가”를 함께 본다

ANDROID MOBILE

62 → 53 → 51

Widevine · offline license · lifecycle/PiP/background를 실기에서 검증한다. App팀은 Android 7 고착 실기 확보가 어렵다고 보고 검증 하한 8 제안을 TIM 협의안으로 둔다.

IOS / IPADOS

62 → 53 → 52

AVPlayer · FairPlay · persistent key를 검증한다. App팀 Matrix는 RFQ iOS 14와 달리 현 Toolchain에서 실질 검증 하한을 iOS 15로 제안한다.

TVOS

64 → 52 재사용

5차 핵심은 새 Player보다 52의 tvOS 재사용 가능성이다. Apple TV HD는 하드웨어 하한 확인에는 유효하지만 App팀 분석상 tvOS 12 재현 검증 수단은 되지 않는다.

App과 Player가 같이 닫을 결정: 지원 OS 하한은 “deployment target 설정 가능”만으로 확정하지 않는다. 실제 연결·실행·DRM 재생 Evidence가 가능한 버전과 시장/필드 요구를 함께 보고 확정한다.

09 · Legacy Runtime Gate

오래된 SmartTV Runtime이 54.player-js의 실제 지원 하한을 결정한다

왜 별도 Gate가 필요한가
1JS / Web Engine예: webOS 4.x는 Chromium 53. 최신 문법·API는 transpile/polyfill로 일부 대응 가능하지만 Runtime 차이는 남는다.
2MSE / EME / DRMpolyfill로 해결할 수 없는 영역. JavaScript 실행 성공과 실제 DRM 영상 재생 성공은 별개다.
3Player VersionShaka는 MSE/EME에 의존하고, 구형 TV/STB의 MediaSource 제약이 HLS 지원에 직접 영향을 줄 수 있다.
4HW / PerformanceCPU·RAM·decoder 성능이 낮아 UI·GC·DRM·영상 재생이 동시에 돌 때 병목이 발생할 수 있다.
Compatibility Probe · oldest target first
